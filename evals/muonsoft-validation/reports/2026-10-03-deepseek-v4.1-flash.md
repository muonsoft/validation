# Validation skill evaluation — 2026-10-03

The skill reduced observed token volume on this sample, with nearly unchanged
correctness. One recurring batch-path failure motivates a focused documentation
correction. This report describes the **original skill and 12-case suite**, before
that correction and the expansion to 15 cases. The revised skill has no new model
results yet.

[Machine-readable results](2026-10-03-deepseek-v4.1-flash.json) contain per-attempt
outcomes, normalized token counters, hashes, and paired summaries. Raw event logs,
credentials, provider configuration, session databases, and worker workspaces are
excluded from this public report.

## Setup and provenance

- Model: `opencode-go/deepseek-v4.1-flash`; no explicit reasoning variant.
- OpenCode: `2.0.18`; Go: `go1.27.1 linux/amd64`.
- Design: 12 cases × two variants × three repetitions, 72 attempts. Identical
  prompts, fresh sessions, alternating variant order by repeat, isolated worker
  filesystems, and hidden independent tests.
- Baseline had no public skill; treatment had only `muonsoft-validation` available
  as a user skill. Both could inspect library implementation source.
- Every graded solution was checked with the race detector against `v0.19.0` and
  the current library snapshot. A pass requires every requirement on both.
- Recorded HEAD: `341aded02f81402997d57bdb9e438cda1b0f365c`, with uncommitted
  OpenCode v2 runner changes later committed as `bf05908`. Content hashes in the
  accompanying JSON identify the measured materials independently of HEAD.
- Skill SHA-256: `523b12389edcc12fffbbab96ebbda753f2ca304448f41af560e31e0f31d06f67`.
- The aggregate combines `validation-eval-v2-full-02` and
  `validation-eval-v2-full-03`; model, skill, runner, suite, Go version, and library
  hashes matched. Earlier smoke and cancelled runs are excluded.

The original run stopped after 29 graded attempts and one interrupted attempt;
the continuation ran the remaining 42 attempts. No attempt was silently retried.
The public JSON includes hashes of the private source manifests and analyses.
Those hashes support artifact identity, but do not make private logs independently
available to readers.

## Correctness and skill selection

| Variant | Attempts | Graded | Passed both versions |
| --- | ---: | ---: | ---: |
| Without skill | 36 | 35 | 32 |
| With skill | 36 | 34 | 31 |

The unequal denominators come from execution failures. In the **33 complete
pairs**, treatment improved one result, regressed none, and left 32 unchanged
(30 pairs passed on both sides; two failed on both sides). The paired difference
is +3.03 percentage points, based on only one discordant pair.

The improvement was `02-collection`, repeat 2: baseline attached uniqueness
violations to elements instead of producing the required collection-level
violation. The other two repetitions passed in both variants.

All five graded `07-batch` solutions omitted the `references` path segment:
`input[0]` instead of `input.references[0]`. Treatment failed three repetitions;
baseline failed two and had one provider failure. `TestBatchIndices` failed on
both library versions; the other requirements passed. The prompt explicitly
required `references[i]` and preservation of the caller prefix. This is a real
contract failure in both variants, not evidence that the skill caused it.

All other graded scenarios passed. The skill was observably loaded in all 32
graded applicable treatment attempts and in no baseline attempt. Both completed
treatment negative controls avoided loading the skill and preserved the existing
validation; the third had a provider failure. This is limited evidence of
appropriate selection, not a broad false-positive estimate.

Codex reviewed all 69 graded solutions using the same four-criterion rubric.
Reviews were not blinded to treatment. Subjective scores were kept separate from
test outcomes and did not turn failures into passes.

## Missing evidence and limitations

Three attempts were ungraded: `05-stages-with-3` was interrupted following a socket
closure; `07-batch-without-1` ended with a provider stream lacking `finish_reason`;
`12-control-with-2` returned provider HTTP 400. Their partial usage is not a complete
cost estimate and is excluded from the primary comparison. The public per-attempt
usage retains unknown counters where the saved manifest lacked usage; partial raw
log reconstruction is not included.

There were only 12 distinct tasks, with three repetitions each, on one model and
one configuration. Repetitions of the same task are not independent task samples.
Most baseline solutions already passed. The single correctness improvement and
observed token reductions do not establish a general or statistically reliable
benefit for other tasks or models. Filesystem isolation and transcript inspection
found no reads of hidden tests, reference solutions, or another variant's skill;
this does not establish isolation from every possible network-side influence.

## Corrections following this run

- Explain batch path composition with an executable example: caller prefix,
  collection property, then original index; avoid repeating an already supplied
  collection property.
- Strengthen batch tests to verify lookup IDs and paths with no prefix and a nested
  prefix. Keep the original failing path requirement.
- Add an already-scoped batch scenario and two negative controls involving error
  presentation and copying messages. These are new follow-up cases, not measured
  results or an independent holdout.
- Include paired token summaries in the runner and support explicit continuation
  of unstarted attempts with matching provenance, preserving earlier artifacts.

The next behavioral evaluation should compare the revised skill with baseline
and the previous skill revision, preserving each revision's results separately.
A further independently authored holdout would be needed to assess generalization
beyond these failure-informed follow-up cases.
